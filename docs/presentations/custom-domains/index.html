DNS · part 1

DNS is the internet's contacts app

Computers find each other by number, an IP address. People remember names. DNS turns the name into the number.

leelagarden.com.np

169.58.157.28

Registrar

Where the name was bought: the .np registry. It records which nameservers are in charge. Yours: eugene and kara.ns.cloudflare.com.

Nameservers · Cloudflare

Hold your records, the actual answers, such as “leelagarden.com.np is at 169.58.157.28”. You edit them in Cloudflare.

Resolver

Does the asking for the visitor: their router, Google (8.8.8.8) or Cloudflare (1.1.1.1). It remembers answers for a while, the TTL.

Three different parties are involved, and mixing them up is the source of most DNS confusion. The registrar is only consulted to find out WHO holds the records (the nameservers). Cloudflare holds the records themselves. Resolvers ask on the visitor's behalf and cache what they hear. When you change a record in Cloudflare, resolvers that cached the old answer keep using it until its TTL runs out.

Your Domains page

The two records, explained

A

Where the site lives

Name

@, the root itself: leelagarden.com.np

Value

169.58.157.28

Who uses it

Every visitor's browser, to find your VPS

TXT

Proof that you own it

Name

_atrium-verify.leelagarden.com.np

Value

atrium-verify=jBqc0F…, a random code made for this domain

Who uses it

Only Atrium's Verify button. Visitors never see it.

A root domain needs an A record (a number). Subdomains such as www can use a CNAME (a nickname pointing at another name). In Cloudflare keep the cloud grey, “DNS only”, so visitors reach nginx directly.

The @ sign is DNS shorthand for "the domain itself", with nothing in front. The A record is the one that actually sends visitors to your server. The TXT record does nothing for visitors; it is a note that only someone who controls the domain's DNS could have written, which is why Atrium uses it as proof of ownership. Root domains cannot use a CNAME by the DNS rules, which is why Atrium asks for an A record here. Grey cloud matters: with the orange cloud, visitors talk to Cloudflare instead of nginx, and certificate checks behave differently.

DNS · lessons from launch day

Why it “didn't work” for a while

What you sawWhyThe fix
Some visitors got errors or an old pageAn old Cloudflare zone in another account still answered for leelagarden.com.npDelete the old zone. Only the one using the registrar's nameservers (eugene and kara) counts

Odd HTTPS errors with the orange cloud onProxied mode puts Cloudflare between visitors and nginx, with its own certificate and rulesKeep the record grey: “DNS only”
Verify said “not pointing”The VPS's own resolver had stale answers, and Atrium misread .com.np as a subdomainVPS switched to 1.1.1.1 and 9.9.9.9; Atrium's code fixed
The big lesson: DNS has memory everywhere. Every resolver caches answers, including "this name does not exist" (negative caching), so after a change different people can see different results for a while. And two Cloudflare zones for the same domain can both exist; only the one whose nameservers are listed at the registrar is real, but resolvers that cached the old nameservers keep asking the old zone until their cache expires. When something looks inconsistent, check with dig against 1.1.1.1 and 8.8.8.8 before changing anything.

Verify does two independent DNS lookups from the server. Ownership: the TXT record must contain exactly the code Atrium generated for this domain. Pointing: the domain's A records must include the server's address, 169.58.157.28 (or, for a subdomain, a CNAME to the platform address). Only when both pass does the domain become Active, and the first time that happens Atrium records the verification date and announces a domain.verified event.

Why the TXT record exists

Anyone can type a domain into a dashboard. Only its owner can change its DNS.

Without the TXT check, a stranger could claim leelagarden.com.np on their own Atrium account. If someone grabs a domain first, the real owner adds a second TXT record, a claim code, and takes it back.

This is the whole idea of domain verification, used by Google, Microsoft, Vercel and others too: ask for something only the owner can do. Editing the domain's DNS is that thing. Atrium also refuses platform names (like admin.sites.surajthapa247.com.np), so nobody can attach those to a client site.

The server

Arriving at 169.58.157.28: the front door

Open to the internet

22 · SSH: you, and the GitHub deploys

80 · HTTP: redirects to HTTPS, certificate checks

443 · HTTPS: every real visitor

Closed: inside the server only

3000 admin app · 3001 renderer · 4000 API

5432 Postgres · 6379 Redis

Reachable only from the server itself (127.0.0.1) and its Docker containers.

The firewall is ufw. Because the apps hide behind it, the only way in from outside is through nginx on 80 and 443.

A port is a numbered door on a server. The VPS has one public address but many programs; each listens on its own port. The firewall (ufw) only opens 22, 80 and 443 to the world. The apps listen on 127.0.0.1, the server's "talk to myself" address, and Postgres and Redis accept only the Docker network. So even if someone knew the database password, they could not reach the database from the internet.

The server

nginx: the receptionist who reads the name

Many sites share one IP address. nginx reads which name the visitor asked for and follows the matching rule.

http://leelagarden.com.np

Redirect to https://, the secure version

https://www.leelagarden.com.np

Redirect to https://leelagarden.com.np

https://leelagarden.com.np

Renderer · 127.0.0.1:3001, the website

https://admin.leelagarden.com.np

Admin app · 127.0.0.1:3000, the dashboard

https://api.sites.surajthapa247.com.np

API · 127.0.0.1:4000

The rules for this domain live in /etc/nginx/atrium-domains/leelagarden.conf on the VPS.

nginx is a reverse proxy: it is the only program facing the internet, and it forwards each request to the right app behind it. With HTTPS it learns the requested name at the very start of the connection (that is called SNI), so it can also pick the right certificate. Plain http and www both get a 301 redirect, which tells browsers and Google that https://leelagarden.com.np is the one true address.

The server

HTTPS: how the padlock was earned

1

certbot, on the VPS, asks Let's Encrypt for a certificate for leelagarden.com.np.

2

Let's Encrypt replies: “prove it. Put this random file under /.well-known/ on that domain.”

3

It fetches the file over port 80. DNS sends it to your VPS, and nginx serves the file.

4

The file matches, so the certificate is issued. It lasts 90 days; certbot renews it automatically.

Privacy: nobody on the café Wi-Fi can read or change the page.

Identity: the certificate proves this server really is leelagarden.com.np.

A certificate is a signed statement: "the holder of this key is leelagarden.com.np". Browsers trust Let's Encrypt's signature, so they trust the certificate. To issue it, Let's Encrypt needs proof you control the domain, and the simplest proof is serving a file it asks for on that domain (the HTTP-01 challenge). That is why port 80 stays open and why the DNS must already point at the VPS before a certificate can be issued. Your certificate files are in /etc/letsencrypt/live/leelagarden on the server.

One honest caveat

“SSL Active” in the dashboard is a label, not the certificate

What the dashboard knows

DNS is right: the TXT matches and the A record points at 169.58.157.28. Atrium then marks SSL “Active”, because it was built for an edge server (Caddy) that issues certificates on its own.

What actually serves HTTPS

On your VPS it is nginx, with the certificate certbot issued. I added the certificate and the nginx rules by hand:

/etc/letsencrypt/live/leelagarden

So each new client domain still needs its nginx rules and a certificate on the server. That can be automated later, for example with Caddy's on-demand certificates or a small script.

Atrium's code assumes an edge like Caddy with on-demand TLS: it would ask Atrium "is this domain allowed?" and issue a certificate automatically the first time a visitor arrives. Your production setup uses nginx and certbot instead, because you asked for the app only. The platform's own subdomains (anything.sites.surajthapa247.com.np) can share one wildcard certificate once a Cloudflare API token is placed on the server; client domains like leelagarden.com.np need their own certificate each.

Building the page

The renderer: from a name to a page

1 · nginx

Hands it over

The request reaches the renderer (port 3001) with the website's name attached, in the Host header.

2 · API

Which website?

The API matches the name to a verified custom domain, or to a platform address (leela-garden is the site's slug).

3 · Postgres

What's published?

The API reads the last published version: pages, theme, text, images. Drafts never leak.

4 · Renderer

Draw and remember

It builds the HTML and keeps a cached copy, so the next visitor gets it instantly. Publishing clears the cache.

About your setup today

nginx tells the renderer “this is leela-garden.sites.surajthapa247.com.np” instead of passing leelagarden.com.np through. Both lead to the same website. Passing the real name through later would let Atrium apply its own primary-domain and redirect rules.

The renderer is a Next.js app that can draw any Atrium website; the name in the request decides which one. It asks the API at /v1/public/sites/resolve?host=... and gets back a snapshot of the last published version. It caches the result, so a busy site barely touches the database. When you click Publish, Atrium tells the renderer to forget its copy, and the next visitor sees the new version.

Case study · reCAPTCHA

How the contact form tells humans from bots

reCAPTCHA v3 is invisible: there is no checkbox. It uses two keys. The site key is public and goes into the page so Google's script knows which account it is working for. The secret key stays on the server and is only used by the API when it asks Google whether a token is genuine. Google's answer includes a score from 0 (bot) to 1 (human) and the hostname the token was made on; Atrium rejects scores under 0.5 and hostnames that aren't allowed. If any link in this chain breaks, the form refuses the message.

Case study · reCAPTCHA

Three things were wrong, one after another

1 Not published

Why

reCAPTCHA was switched on in the draft, but visitors get the published version, where it was still off.

Fix

Publish the website.

2 Site not allowed

Why

Atrium accepts tokens only from listed names, matched exactly. The .sites address wasn't listed.

Fix

Add this to Atrium's Allowed hostnames:

*.sites.surajthapa247.com.np

3 A hidden space

Why

The pasted site key ended in a space. Google received …9lE%20, refused the key and never gave a token.

Fix

Trim it, clear the cached page, and make Atrium trim keys from now on.

Two lists, two jobs

Google's console: surajthapa247.com.np and leelagarden.com.np. Subdomains are included; wildcards are rejected. Atrium: matches exactly, so it needs the *.sites wildcard.

Each problem hid the next one. Until the site was published, there was no reCAPTCHA on the page at all. Once it was there, submissions from the .sites address would have been refused because Atrium's allow-list did not include it. And even then, Google refused to issue any token because the site key had a trailing space: %20 is how a space looks inside a web address. That last one is invisible on screen, which is why it took the longest. The code fix (commit 1af7b6f) trims spaces from the site key, secret key and hostnames whenever they are saved.

Case study · reCAPTCHA

How I tracked it down

1

Read the live page's HTML. No reCAPTCHA at all. The draft had it on, the published version didn't, so the website was published.

2

Read the captcha integration. Its allowed hostnames missed the .sites address. I added it, re-entering all four, because the edit form hides saved ones.

3

Looked at what the form really received, in Chrome. The site key ended in a space. I trimmed it in the database.

4

Cleared the renderer's cached page and watched Google issue a token. Working. The code now trims keys, so it can't recur.

Lesson: check what visitors actually get, the live page, not what the editor shows. And invisible characters are real.

The method matters more than the specific bugs: start from what the visitor's browser actually receives and work backwards. Step 1 compared the live HTML with the draft. Step 3 read the settings the form component was given inside the browser, which is where the trailing space finally showed up. After changing the database directly, the renderer still had the old page cached, so it had to be told to refresh. One thing is still open: the captcha edit form does not show already-saved hostnames, so saving it can wipe them. That is flagged as a separate fix.
